# 方案C · 全程均匀掉电的电量显示 · 设计

**设备**：popsicle / FCC=6208mAh / 电量计 Term Voltage=3030mV
**目标**：降关机电压后，电量百分比在 **100%→0% 全程按同一 mAh 刻度均匀下降**，
手机恰好在 0% 时到达新的关机电压，而不是「先正常掉到 0%，再额外送一段」。
**日期**：2026-08-04　**状态**：设计定稿，待实现（依赖方案B 内核模块先生效）

---

## 一、为什么原方案（只改最后 5%）是错的

原设计（`方案B` §四配套 / `交接提示词` B 部分）：
```
真实soc > 0            → fake_soc = -1（透传）
真实soc = 0 且 V>2600  → fake_soc = round((V-2600)/(3030-2600)*5)
```
三个缺陷：

1. **会向上跳变**。真实 soc 从 1% 掉到 0% 的瞬间 watchdog 才接管，
   而此时 V≈3030 → 合成值 = round(430/430*5) = **5%**。
   用户看到的是 `1% → 5%`，**百分比往上跳**。这是最刺眼的 bug。
2. **刻度不守恒**。底部那段真实容量约 150mAh（≈总量的 2.4%），却被硬拉伸成「5%」。
   前 100% 每格 62mAh，最后 5 格每格 30mAh —— 掉电速率在 0% 附近突然减半。
3. **上半段完全没变**。100%→0% 仍按老刻度跑完，多出来的电是「附赠」的，
   不是「摊进全程」的。这正是你要求要改掉的。

## 二、正确模型：全程按 mAh 重标定

把电池看成两段，用**同一把 mAh 尺子**去量：

```
  ┌──────────────── 上段 Q_top = FCC = 6208 mAh ────────────────┬─ 下段 Q_bot ─┐
4.45V                                                        3030mV        2600mV
  │                    rm 从 FCC 线性降到 0                      │  rm 恒为 0   │
  └─────────────────────────────────────────────────────────────┴─────────────┘
```

**核心公式（唯一一条）**：
```
display% = 100 × (rm + qbot_now) / (FCC + QBOT)
```
- `rm`      = `fg_master/rm`（mAh），上段剩余，电量计给
  （**更好的输入**：`strategy-fg/raw_soc` = `rm/FCC × 10000`，厘百分比，实测三次精确相等；
   用它可写成 `display% = (raw_soc/10000 × FCC + qbot_now)/(FCC+QBOT) × 100`，免掉整数取整误差）
- `QBOT`    = 下段总容量（mAh），**标定值**，初始估计 150
- `qbot_now`= 下段剩余（mAh），上段未耗尽时恒 = QBOT

性质（正是"均匀"的定义）：
- rm=FCC 时 → 100%
- rm=0（3030mV）时 → `QBOT/(FCC+QBOT)` = 150/6358 = **2.4%**，**连续，无跳变**
- qbot_now=0（2600mV）时 → 0%，**恰好在关机电压归零**
- 全程每 1% = `(FCC+QBOT)/100` = 63.6 mAh，**上下段同一刻度**

对比原方案：底部占比从假的 5% 变成真实的 2.4%，上段每格从 62.1 → 63.6 mAh
（整条曲线被压缩 2.4%，肉眼几乎无感），多出来的电**摊进了全程**。

## 三、下段剩余量 `qbot_now` 从哪来（关键实现点）

**先确认没有现成节点**——已用真机数据证实：
```
charge_counter 5337000 / charge_full 7210000 = 74.02%
rm             4596000 / FCC        6208000 = 74.03%   ← 完全一致
```
→ `battery/charge_counter` 是 `rm/FCC × charge_full` 的**派生量**，
   和 rm 一起在 3030mV 触底，**不是独立库仑计**。
   `fg_master/` 下也没有裸库仑计节点（只有 rsoc/rm/qmax/soh 等派生量）。

### 用电压映射，不用运行时库仑积分
```
qbot_now = QBOT × f(Vocv)      // f: 1→0 的归一化曲线，定义域 [VCUT, VTERM]
```

**为什么电压在这一段是对的传感器**：下段 OCV 曲线**极陡**——150mAh 铺在 430mV 上，
约 **2.9 mV/mAh**。电压在中段不能用来测电量是因为中段平坦；在陡段电压恰恰是最好的指示器。

**为什么不用运行时积分**（曾考虑，已否决）：
- 积分要**维护状态**：watchdog 重启 / 手机重启 / 进程被杀 → `qbot_now` 丢失，无从恢复；
  电压映射**无状态**，任何时刻重新算都得到正确值
- 电流零点漂移会在长时间积分中累积
- 需要一个「何时进入下段」的触发边沿（rm→0），rm 抖动会误触发

### ★必须做 IR 补偿（否则会出现跳变）
终端电压 ≠ 开路电压。大电流时内阻压降把电压拉低，
在 2.9mV/mAh 的陡区，压降会被直接读成"电量少了"。
不补偿的表现：开游戏电压一沉、百分比掉几个点；退出游戏又想涨回来（被 §四 单调钳制成"卡住"）。

```
Vocv = V + |I| × R_int
```

**R_int 已实测（2026-08-04，负载阶跃法，52% SOC / 36.5°C）**：
```
空载 8 样本: V≈3846.4mV  I≈ -82.7mA
满载11样本: V≈3820.3mV  I≈+1272.1mA
ΔV=-26.1mV  ΔI=+1354.9mA  ->  R = 19.3 mΩ
```
- 该条件下 3A 负载 → 58mV → ~20mAh → **0.31 个显示百分点**（比原估的 0.65 小）
- **但底部 R 会显著变大**（低 SOC + 低温，通常 2~3 倍）→ 到 2.6V 附近可能 40~60mΩ，
  重新回到 0.6~1.0 个点。**所以 IR 补偿必须保留**，且 R_int 要在**底部标定**（§七），
  52% 处测的值不能直接拿去用

**`fg_master/calc_rvalue = 3237` 不是 R_int**（已排除）：
按 0.01mΩ 解读 = 32.4mΩ，与实测 19.3mΩ 差 1.7 倍，按 µΩ 解读 = 3.2mΩ 更离谱。
另有 `resistance_id = 100000` 是电池 ID 电阻（100kΩ），也不是。→ 老实标定，别用这两个节点。

**连续性校验**（这是全案的关键性质）：
- `Vocv = VTERM(3030)` → `f=1` → `qbot_now = QBOT` → 与 `rm=0` 的边界**严丝合缝**
- `Vocv = VCUT(2600)`  → `f=0` → `display = 0`，**恰好在关机电压归零**

`f` 的初始形态取**线性**（`f = (Vocv-VCUT)/(VTERM-VCUT)`）；
标定放电后换成实测查表（§七），因为真实 OCV 在 2.7V 以下会明显加速下坠。

## 四、完整算法

```
常量/配置：
  VTERM = 3030            // 电量计 Term Voltage，rm 触底点
  VCUT  = 读自内核模块 module_param（不写死，见 §六）
  QBOT  = 标定值，默认 150 mAh
  R_INT = 标定值，默认 40 mΩ
  TICK  = 上段 30s / 底部段 2s（自适应，见 §四之二）

状态：last_disp（仅用于单调/限速，丢了也能自愈）

每 tick：
  V   = voltage_now / 1000            // mV
  I   = current_now / 1000            // mA，★本机 + = 放电，− = 充电（两次独立实验坐实）
  rm  = fg_master/rm / 1000           // mAh
  FCC = fg_master/charger_full / 1000 // mAh
  dsg = (I > 0)      // ★用电流符号判方向，不能用 status（见 §四注）

  # --- 0) 安全闸：模块没生效就不化妆 ---
  if 模块未加载 or VCUT 读不到:
      write fake_soc = -1 ; continue        // 关机点仍是 3030，假装有底部电量会误导

  # --- 1) 交还关机通道（硬性，见 §六）---
  if V <= VCUT + 50:
      write fake_soc = -1 ; continue

  # --- 2) 下段剩余量：无状态电压映射（含 IR 补偿）---
  Vocv     = V + abs(I) * R_INT / 1000       // mV
  qbot_now = QBOT * clamp( f(Vocv), 0, 1 )   // f 初始为线性，标定后换查表

  # --- 3) 唯一的显示公式 ---
  disp = 100 * (rm + qbot_now) / (FCC + QBOT)

  # --- 4) 单调 + 限速（防电量计抖动导致百分比乱跳）---
  if first_tick:  pass
  elif dsg:       disp = min(disp, last_disp)   // 放电中禁止上升
  else:           disp = max(disp, last_disp)   // 充电中禁止下降
  disp = clamp_rate(disp, last_disp, 1% / 30s)

  # --- 5) 只在整数变化时才写，减少无谓 I2C/sysfs ---
  d = round(disp)
  if d != last_written:  write fake_soc = d
  last_disp = disp
```

## 四之二、轮询开销与自适应 tick（实测驱动）

### 实测：哪些节点贵，为什么
`tools/poll_cost_probe.sh` 两种方法互证（`/proc/uptime` 121µs = shell 循环本身的基线）：

| 节点 | µs/次 | 判定 |
|---|---|---|
| `battery/capacity` | 90 | **缓存，免费** |
| `strategy-fg/raw_soc` | 108 | **缓存，免费** |
| `battery/temp` / `status` / `soc_decimal` | 72 / 111 / 89 | **缓存，免费** |
| `battery/voltage_now` | **2244** | 真 I2C |
| `battery/current_now` | **2156** | 真 I2C |
| `fg_master/rm` | **2146** | 真 I2C |
| `fg_master/charger_full` | **2061** | 真 I2C |
| `strategy-fg/pack_vbat` / `fg_master/vbatt` / `average_current` | 1133 / 1982 / 1902 | 真 I2C（**无缓存版 V/I**）|

**I2C 事务计数交叉验证**（kprobe on `i2c_transfer`）：
基线 108/s（= 驱动自身 5Hz 轮询），加上 1Hz×6 节点后只增加 **4.3/s**——
6 个节点里恰好 4 个属于 2ms 那批 → 4 次/秒，**两种测法完全对上**。

**驱动自身节奏 = 5Hz**（`check_shutdown_delay` 10s 命中 54 次），与步骤0 的 178ms 间隔一致。

### 为什么 1Hz 是浪费
- 1Hz × 4 个 I2C 节点 × 2.1ms = **8.4ms/s ≈ 0.84% 单核**常驻，折算约 **0.1%/天**（不致命，但没必要）
- **1% = 63.6mAh，500mA 负载下要走 7.6 分钟** → 30s tick 已有 15 个采样点/百分点，
  **1Hz 是过采样 450 倍**

### ★自适应 tick（关键优化）
**上段 `rm>0` 时 `qbot_now ≡ QBOT` 是常数，公式退化成只依赖 `raw_soc` 和 FCC**
→ **上段完全不需要读 V/I，零 I2C**：
```
上段（raw_soc > 0，占约 97% 的时间）：
    tick = 30s，只读 raw_soc（108µs 缓存）
    FCC 每 10 分钟刷一次（只在学习周期才变）
    -> 稳态开销 ≈ 0.0004% 单核，实质为零

底部段（raw_soc == 0，一次放电约 18 分钟）：
    tick = 2s，读 V/I（各 ~2.1ms）
    -> 2.1ms×2/2s = 0.21% 单核，且只在底部这一小段
```
息屏后系统进 suspend，shell 的 `sleep` 被冻结不触发唤醒，**待机无额外开销**。

### 进一步（等内核模块就位后）
模块本就 hook 了 `check_shutdown_delay`、手里有 struct 指针，
而 `[0x844]`(均值电压) / `[0x838]`(电流) **本来就是驱动 5Hz 更新好的缓存值**。
让模块把它们以只读 module_param 导出 → watchdog 底部段读取降到 ~100µs、**零额外 I2C**。
（策略仍留在用户态便于迭代，模块只负责把已有的缓存值暴露出来。）

### ★§四注：为什么判方向必须用电流符号，不能用 `battery/status`
实测（2026-08-04 断充实验）：撤销 input_suspend 恢复充电后，
`status=Charging` 但 `current_now=+1120000`（正=放电）——**充电状态下电池仍在放电**。
原因在 votable：`buck_input: volt_limit en=1 v=500` → **输入电流被限到 500mA**，
系统负载一旦超过 500mA，差额就由电池补，于是 status 与真实电流方向脱节。

→ `status` 反映的是**充电器状态**，不是电池电流方向。单调钳制要的是物理真值，**用电流符号**。

**电流符号约定（两次独立实验坐实）**：**正 = 放电，负 = 充电**
1. 负载阶跃：加载 8 核 → 电流变正(+1272mA) 且电压下降 → 由 `V=OCV−I·R` 知正必为放电
2. 强制放电：input_suspend 挂起输入 → status=Discharging → I=+824mA

## 五、为什么这样不会被内核的平滑层干扰

`fake_soc` 在 `strategy_fg_ops_get_soc` **出口**覆盖返回值，
绕过了 `fg_ui_soc_smooth` 的全部平滑/防跳规则（"not allow ui_soc jump to 0"、
"keep constant by current_mean/plugin_time" 等）。
→ 我们写什么，上层就显示什么，**平滑责任完全转移到 watchdog 自己**（§四 step 4 就是补这个）。

同时（步骤0 已实测）：`check_shutdown_delay` 的入参 ui_soc 取的是**内部** ui_soc，
不经 fake_soc，所以显示 2%~0% **不会**干扰电压闸判定。

## 六、与关机 uevent 的交接（硬性约束）

`check_shutdown_delay@0x9634`：`fake_soc != -1` → **跳过发 `POWER_SUPPLY_SHUTDOWN_DELAY` uevent**。
内核不自己关机，靠这条 uevent 通知用户态拔电。
→ **底部必须把 fake_soc 写回 -1**，否则关不了机（§四 step 1）。

交接点设在 `V <= VCUT + 50`：
- 此时 display 已经是 0~1%，交还后显示内核真实 ui_soc（=0），**视觉连续**
- 关机通道交还内核，由电压闸正常触发

`VCUT` **必须从内核模块的 module_param 读**，不能在脚本里写死——
两边一旦不一致，要么提前黑屏（watchdog 以为还有电），要么关不了机。

## 七、标定流程（QBOT / R_INT / f 三个参数，一次深放全部拿到）

运行时不做积分，但**标定时用积分**——这是电流积分唯一的用武之地，离线一次性。

1. 模块设保守档（先 2900），watchdog 用默认 QBOT=150 / R_INT=40mΩ / f=线性 跑
2. 从 `rm` 归零那一刻起，1Hz 记录 `t, V, I, rm` 到 CSV，直到关机
3. **QBOT** = `Σ |I| × dt / 3600`（整段积分）
4. **R_INT**：找电流突变点（灭屏/亮屏、启动应用），`R = ΔV / ΔI`，取中位数。
   **必须在底部测**——52% 处实测 19.3mΩ，但低 SOC + 低温下 R 会涨 2~3 倍，
   用 52% 的值去补偿底部会补不够
5. **f 查表**：用 IR 补偿后的 `Vocv` 对「已放出 mAh / QBOT」作图 → 得真实曲线，
   替换线性近似（真实 OCV 在 2.7V 以下会明显加速下坠，线性会高估底部余量）
6. 逐档下探（2800/2700/2600）各测一次，QBOT 随截止电压增大

**标定期间显示会略有偏差**（底部那 2~3% 走快或走慢），
但**不会跳变**，因为公式本身连续。这也是先用保守档 2900 的原因。

## 八、阶段2（可选）：能量加权，让"每小时掉几个点"真正恒定

§二 是 **mAh 均匀**。但手机近似恒功率放电，续航 ∝ ∫V·dq，
而 V 从 4.45 降到 2.6 —— 同样 1mAh，在顶部买到的续航是底部的 ~1.35 倍。
所以 mAh 均匀 ≠ **时间**均匀（这一点在原生显示上本来就存在，不是本方案引入的）。

真正的时间均匀：
```
display% = 100 × E_remaining / E_total,   E = ∫ V dq
```
需要一条 `V(soc)` 曲线，用 §七 标定 + 一次完整放电记录即可建出来。
**建议先上阶段1**（正确、简单、立刻可实现），拿到真实放电曲线后再决定要不要上阶段2。

## 九、失效保护（必须实现）

| 风险 | 处理 |
|---|---|
| watchdog 挂掉 → fake_soc 卡在旧值 | `trap EXIT/INT/TERM → echo -1 > fake_soc`；service 循环拉起 |
| watchdog / 手机重启后不知道自己在哪 | **不存在**——§三 是无状态电压映射，重算即正确（这正是否决积分的主因）|
| 模块没加载却在化妆 → 3030 就黑屏 | §四 step 0：读不到模块 param 就写 -1 不化妆 |
| QBOT 标定错 → 底部走快/走慢 | 公式连续，最差只是速率偏差；不会跳变、不会误关机 |
| 大电流压降导致百分比乱动 | §三 IR 补偿 + §四 单调/限速 |
| 电量计 rm 抖动 | §四 step 4 单调 + 限速 |
| VCUT 与模块不一致 | §六：VCUT 只从 module_param 读，不写死 |

## 十、预期效果（诚实的数字）

- 3030mV→2600mV 多榨出的容量 ≈ **150mAh ≈ 总量的 2.4%**（待 §七 实测）
- 用户可见变化：**手机在 0% 关机，而不是在 0% 之后还能跑 20 分钟**；

## 附：被排除的替代方案
**改电量计 DF 的 Term Voltage（3030→2600）** 才是根因修复：
电量计自己就会把下段算进 rm/FCC，rsoc 天然正确，**完全不需要 watchdog**。
但这要写电量计 DF，触碰安全红线（`方案B` §七：保留电量计固件+PMIC 硬件过放保护），
且 FCC 需若干学习周期才收敛。**不采用。**
