### 2. 反汇编解出两个写入口的格式
**`mac_addr`（写 DF，关键）** — `fg_parse_mac_addr_para` @0x7ba0：
- 输入按 `%02x ` 空格分隔解析，最多 0x24=36 token
- token0,token1 → 16-bit MAC 块地址（小端：addr = tok0 | tok1<<8），存 [chip+0x294]
- token2.. → 数据，存 [chip+0x296]
- 末尾 `__fg_mac_write_block(chip, addr, &data, len=0x20)` 固定写 32 字节，失败重试 3 次
- 即：`echo "LO HI D0 D1 ... " > mac_addr` 向 DF 块地址写 32 字节（校验和由驱动算）

**`free_addr`（裸 I2C 块写）** — `fg_parse_free_addr_para` @0x7d7c：
- token0 = 数据长度 N（校验 token0+2 == 总token数）
- token2 = 寄存器地址；token3.. = 数据
- 末尾 `__fg_write_block(chip->i2c, reg=tok2, data=&tok3, len=N-1)`，重试 3 次

**`fg_set_one_cutoff_voltage` @0xaf64**：直接写 DF 块 **0x004F**（低电量档）/**0x0050**（另一档），len=2，失败日志 `could not write term_voltage`。对应读 = `fg_get_one_cutoff_voltage` 读 0x004F/0x0050。→ 证实报告里「DF block 0x004f = 3030 = Term Voltage」这块**确实是截止电压写入目标**，且驱动有独立写函数。

`cutoff_vol` sysfs 当前 = 3030 ✓（与 I2C trace 实测一致）

### 5. ★核心矛盾：旧文档对「764mAh 锁在哪」自相矛盾（用户提醒后复核发现）
旧手册给了两个互斥解释：
- 解释A：「锁在放电侧，3030mV 截止线以下 ~764mAh 用不到」
- 解释B：「764 = charge_full(7209) − FCC(6445)」
这俩是**物理上不同的东西**：
- charge_full(7210) = 驱动上报给 App 的满容量（strategy 层缓存值）
- FCC(6208) = 电量计内部 FullChargeCapacity，RSOC 的分母
- 两者之差 ≠「截止电压以下的容量」，而是「两套账本的差」。763 那个数是巧合/被文档混为一谈。

**技术判断（待用户确认方向）**：
- 「设计7500 vs FCC6208」的缺口，主要来自 ①真实老化（soh_learn 7188→6959→6679，循环369）②截止电压以下正常化学保留（不可避免的几%）③可能有小米保守策略。
- **降 Term Voltage（3030→2800）** 只能多榨底部一点点真实续航（OCV 曲线在 3V 附近很陡，估计百来 mAh），且要经过若干学习周期才反映到 FCC，代价是加速老化 + 安全裕度下降。**它不是大头。**
- **直接写高 FCC/QMax（mac_addr 写 DF）** 只是让百分比「显示」更大，不产生真实能量——手机会以虚高容量跑过真实空点，最后仍撞 DOD 电压关机表。属于「显示解容」不是「真解容」。

→ 「解容」到底要哪种,要跟用户对齐(真实续航 vs 上报数字),两条路风险/收益完全不同。

### 8. ★★关机判定链路全解（反汇编 mca_strategy_fg_comp + 真机读表）
用户目标：关机电压降到 ~2.6V。用户假设：关机是"电量被写0"触发，不是真没电。
**结论：假设对一半。关机是【两道独立闸】，只改 fake_soc 挡不住电压闸。**

**SOC 覆盖点**（`strategy_fg_ops_get_soc` @0x5718）：
- struct 偏移 `0x94c` = fake_soc；≠ -1 时 ops_get_soc **直接返回 fake 值**
- `set_fake_soc` 钳制 -1..100
- → fake_soc 只改"对外返回/显示"的 SOC，能挡住【UI 到 0% 的有序关机】

**电压闸（fake_soc 挡不住）**：
- `check_shutdown_delay` @0x9424：
  - vpack ≤ **3000mV**(0xbb8) 连续 10 次 → 强制关机（`mca_shutdown_due_to_vpack_low`）
  - 电压[0x844] < vcutoff_shutdown_delay[0x8dc] + 50 → heavy_load_count++ → 关机
  - fake_soc≠-1 时跳过发 `POWER_SUPPLY_SHUTDOWN_DELAY` uevent（有交互但不解除电压闸）
- `update_vcutoff_para` @0x8ad0：按【温度→剩余量】查表得 vcutoff_fw/shutdown_delay/sw，存 [0x8d8/0x8dc/0x8e0]
  - enable_rollback 路径(byte 0x958==1 且电压≤3007)会强制 fallback 到 0xbea/0xbea/0xb54 = **3050/3050/2900**
- 真正执行关机 = 用户态(healthd/powerkeeper) 收 ui_soc=0 + shutdown_delay 信号

**★dod_para / cc_para 表全解**（真机读出，格式 = [剩余量, vcutoff_fw, shutdown_delay, vcutoff_sw]，一张表5档剩余量，dod_para0..4=5个温度带）：

### 10. ★电压闸精确定位（回答用户「电压闸在哪里」）
调用链（xref_scan + 反汇编确认）：
```
fg_update_status @0x4494 ──► update_vcutoff_para @0x8ad0 ──► update_cc_para @0x8878
   (每周期刷新，把 dod_para 表按 温度→剩余量 算出 vcutoff_fw/delay/sw 存 [0x8d8/0x8dc/0x8e0])
   @0x4ab4/0x4ac0 调 platform_fg_ops_get_volt 取电压 ──► str [0x838] (0x4eac)

fg_ui_soc_smooth @0x7ff4 ──► check_shutdown_delay @0x9424   ← ★电压闸判定就在这
   比较: 电压[0x844] < vcutoff_shutdown_delay[0x8dc]+50  → 关机计数
          vpack(power_supply_get_property) ≤ 3000mV ×10  → 强关
   @0x9680 调 mca_event_report_uevent 发 POWER_SUPPLY_SHUTDOWN_DELAY
```
**三个层面回答：**
1. **判定代码在哪**：`mca_strategy_fg_comp.ko` 的 `check_shutdown_delay`(判定) + `update_vcutoff_para`(算阈值)。判定嵌在 `fg_ui_soc_smooth`（电量计算函数）里被调 → 印证用户"写0逻辑在电量计算里"的直觉。
2. **电压从哪来**：`platform_fg_ops_get_volt`（UND → mca_platform_fg_ic_ops.ko → bq27z561 电量计读 pack 电压），存 struct+0x838；vpack 另经 power_supply_get_property。**电压源是电量计芯片**。
3. **谁执行关机**：内核**不自己关机**（模块无 orderly_poweroff/kernel_power_off 符号），只 `mca_event_report_uevent` 发 uevent + 把 ui_soc 压 0 → **用户态 healthd/powerkeeper 拔电**。

**★纠正上轮方案④**：电压闸的电压来自 `platform_fg_ops_get_volt`(电量计)，**不是** mca_vbat_ovp_mon。所以写 `fake_vbat_override` 喂的是 OVP 监控，**大概率喂不到这条关机判定**——方案④对降关机电压不一定有效，需实测。真正的"电压伪装点"是拦 `platform_fg_ops_get_volt` / 电量计读数（→ 指向内核模块 hook）。

**方案表更新**：
- 最干净精确 = **内核模块**：hook `platform_fg_ops_get_volt` 返回略高电压（骗过电压闸），或直接改内核里解析后的 vcutoff 阈值/dod_para 表 → 精确设 2.6V
- fake_temp 选低档表(方案①)仍待确认"温度→档"映射
- fake_soc 仍只挡 UI 闸

### 11. ★续读结论：纯 sysfs 脚本无法降关机电压，必须内核模块
反汇编 `update_cc_para`@0x8878 + `fg_update_status` 温度/循环写入点：
- **选档依据 = 温度[0x850] + 循环[0x84c]**（update_cc_para 按温度带查表、带内按循环次数选子档；电池越老截止越高）
- 温度换算：`[0x850]` 存的是 °C 值，代码 ×(1/10) 说明原始是 0.1°C；`[0x850] = 原始温度 − 温度补偿[0x858]`
- **★关键：选档用的温度/循环都来自"原始电量计读数"([0x970]~[0x984])，不是 fake 节点**
  - `fake_temp[0x950]` 全模块只在 `strategy_fg_sysfs_show`@0x6c40 被读（cat 读回），**不进温度管线**
  - `strategy_fg_ops_get_temp`@0x5fa8 返回 [0x850] 原始值，也不套 fake_temp
  - → **写 fake_temp 改不了选档温度 → 方案①（fake_temp 选低档表）不成立**
- fake_soc 同理只覆盖 ops_get_soc 返回值（显示/UI闸），挡不住电压闸
- **结论：纯 sysfs 脚本（fake_soc + fake_temp）无法把关机电压降到 2.6V。** 两道闸里电压闸的输入是原始电量计电压/温度/循环，脚本层够不着。

### 12. ★最终方案：内核模块（唯一可靠路径）
本机模块签名不强制、无 lockdown，可加载未签名模块。三选一（或组合）：
- **(A) hook `platform_fg_ops_get_volt`**：真实电压 <~3.0V 时返回 +400mV → 电压闸永远看到 >阈值，真实放到 ~2.6V 才触发。改动面最小。
- **(B) 改内核 RAM 里的 vcutoff 阈值**：直接把 strategy 结构体 [0x8d8/0x8dc/0x8e0] 或解析后的 dod_para 表([0x918]/[0x940]) 改成 ~2550mV。最精确、最靶向。
- 配合：fake_soc 或给 ui_soc 兜底，避免 UI 先到 0% 关机。
- 循环伪装（cyclecount→[0x84c]）**或许**能选低一档，但最低档"余量充足"行仍 ~2900mV，且不能任意设 2.6V，不作主方案。

**安全红线（务必保留）**：只放宽软件截止，**保留电量计/PMIC 硬件过放保护**。反复放到 2.6V 加速老化、有析锂风险；min_life_vol=2609 说明电芯到过 2.6V 但不代表可反复。动手写模块前需向用户重申。

### 19. ★再读 check_shutdown_delay 得到的两条被忽略的控制流（影响 watchdog 设计）
1. **`0x94a4/0x9534: cmp w23,#2; b.ge 0x9520`** —— w23 = 入参 `*(int*)x1` = 内部 ui_soc。
   **ui_soc ≥ 2 时函数直接返回，根本不评估电压闸。** 电压闸只在 ui_soc ≤ 1 时才跑。

2. **`0x9634: ldr w8,[x19,#0x94c]; cmn w8,#1; b.ne 0x968c`** —— **fake_soc ≠ -1 时跳过发
   `POWER_SUPPLY_SHUTDOWN_DELAY` uevent**。→ watchdog 若在底部一直写 fake_soc，会**堵死有序关机通道**。
   **修正 watchdog 设计**：只在 `V > 目标+50mV` 时写合成 fake_soc；一旦 `V ≤ 目标+50` 立刻写回 -1，

## 2026-08-04 · 方案C：全程均匀电量显示（用户否决"只改最后5%"）

### 23. ★用户指出原 fake_soc 方案的根本缺陷
原设计「真实soc>0 透传；=0 后按电压映射 0~5%」有三个缺陷：
1. **会向上跳变**：真实 soc 1%→0% 瞬间 watchdog 接管，此时 V≈3030 → 合成值 = 5% → 显示 `1%→5%` 往上跳
2. **刻度不守恒**：底部真实约 150mAh(≈2.4%) 被硬拉伸成"5%"，0% 附近掉电速率突然减半
3. **上半段没变**：多出来的电是"附赠"的，不是"摊进全程"的
→ 用户要求：**整个过程均匀掉电**。落盘 `方案C-全程均匀电量显示-设计.md`

### 24. ★核心公式：全程按 mAh 重标定
```
display% = 100 × (rm + qbot_now) / (FCC + QBOT)
```
- rm=FCC → 100%；rm=0(3030mV) → QBOT/(FCC+QBOT)=2.4%，**连续无跳变**；qbot=0(2600mV) → 0%
- 全程每 1% = (FCC+QBOT)/100 = 63.6mAh，**上下段同一把尺子**
- 底部占比从假的 5% 变成真实的 2.4%；上段每格 62.1→63.6mAh（整条曲线压缩 2.4%，肉眼无感）

### 25. ★实测确认：没有独立库仑计可用
```
charge_counter 5337000 / charge_full 7210000 = 74.02%
rm             4596000 / FCC        6208000 = 74.03%   ← 完全一致
```
→ `battery/charge_counter` 是 `rm/FCC × charge_full` 的**派生量**，和 rm 一起在 3030mV 触底。
`fg_master/` 下也无裸库仑计节点。（数据源：`charge_full_trajectory.csv` 末行，无需连真机）

### 26. ★qbot_now 用无状态电压映射，不用运行时积分（用户否决积分，采纳）
一度设计成 watchdog 每秒积分 `current_now`，用户指出电压映射已足够。**复核后确认用户对**：
- 下段 OCV **极陡**（150mAh 铺 430mV ≈ **2.9mV/mAh**）→ 电压在陡段恰恰是最好的指示器
  （电压在中段不可用是因为中段平坦，与此处情形相反）
- 积分要**维护状态**：watchdog/手机重启 → qbot_now 丢失无从恢复；电压映射**无状态**，重算即正确
- 积分还有电流零点漂移、rm→0 边沿误触发两个问题
```
qbot_now = QBOT × f(Vocv)      // f: 1→0，定义域 [VCUT, VTERM]，初始线性，标定后查表
```
**但必须补 IR 补偿**（否则仍会跳变）：终端电压≠开路电压，3A×40mΩ≈120mV，
在 2.9mV/mAh 陡区 = ~41mAh = **0.65 个显示百分点**；表现为开游戏掉2点、退出想涨回。
```
Vocv = V + |I| × R_int
```
补偿后残差 ≈0.2 个点。**电流积分降级为一次性离线标定**（§七），运行时完全不用。

  「0% 之后还能跑 20 分钟」，**不是续航大幅提升**

### 29. ★★负载阶跃实测内阻 + 纠正电流符号约定
方法：8 核忙循环做负载阶跃，1Hz 采 V/I（全只读，未写任何电池节点）。
```

满载11样本: V≈3820.3mV  I≈+1272.1mA
ΔV = -26.1mV   ΔI = +1354.9mA   ->  R_int = 19.3 mΩ  @52%SOC / 36.5°C
```

**★纠正：本机 `current_now` 正值 = 放电**（不是 Android 惯例的正值=充电）。

→ **方案C 的充放电判定一律用 `battery/status`，不用电流符号**，否则单调钳制会判反。
（也解释了早期 CSV 里 status=Charging 却出现负电流：那是空载时电池在被小电流充。）

**`fg_master/calc_rvalue = 3237` 不是内阻**（已排除）：按 0.01mΩ 解读=32.4mΩ，
与实测 19.3mΩ 差 1.7 倍；按 µΩ 解读=3.2mΩ 更离谱。`resistance_id=100000` 是电池 ID 电阻(100kΩ)。
→ R_int 老实标定，且**必须在底部测**（低 SOC+低温 R 涨 2~3 倍，52% 的值补不够底部）。

**IR 补偿量重估**：19.3mΩ @3A = 58mV = ~20mAh = **0.31 个显示百分点**（原估 0.65 偏大）；

### 34. ★纠正 §29 的建议：判电流方向要用电流符号，不能用 status

原因：votable `buck_input: volt_limit en=1 v=500` → **输入电流被限到 500mA**，
系统负载超过 500mA 时差额由电池补，status 与真实电流方向脱节。
→ `status` 反映**充电器状态**，不是电池电流方向。**方案C 单调钳制改回用电流符号**。

**电流符号最终结论（两次独立实验坐实）：正 = 放电，负 = 充电**
1. 负载阶跃：加载 → I 变正(+1272mA) 且电压下降 → 由 `V=OCV−I·R` 知正必为放电
2. 强制放电：input_suspend → status=Discharging → I=+824mA

## 2026-08-04 · watchdog 轮询开销实测（用户提问驱动）

### 35. ★实测：哪些 sysfs 节点会触发真 I2C
用户问「每秒轮询开销大不大」。两种方法互证（`tools/poll_cost_probe.sh` / `_probe2.sh`）：

**方法1 单次读耗时**（`/proc/uptime` 121µs = shell `read x < file` 循环本身的基线）：
| 节点 | µs/次 | 判定 |
|---|---|---|
| `battery/capacity` | 90 | 缓存 |
| `strategy-fg/raw_soc` | 108 | 缓存 |
| `battery/temp` / `status` / `soc_decimal` | 72 / 111 / 89 | 缓存 |
| `battery/voltage_now` | **2244** | 真 I2C |
| `battery/current_now` | **2156** | 真 I2C |
| `fg_master/rm` | **2146** | 真 I2C |
| `fg_master/charger_full` | **2061** | 真 I2C |
| `strategy-fg/pack_vbat` / `fg_master/vbatt` / `average_current` / `ibatt` | 1133 / 1982 / 1902 / 1443 | 真 I2C |

→ **不存在缓存版的 V/I 节点**（strategy 层的 [0x844]/[0x838] 没有便宜的 sysfs 出口）。

**方法2 I2C 事务计数**（kprobe on `i2c_transfer`）：
- 基线 10s = 1085 次 = **108/s**（驱动自身 5Hz 轮询产生）
- 加 1Hz×6 节点后 = 1128 次 = 112/s，**增量 4.3/s**
- 6 个节点里恰好 4 个属于 2ms 那批 → 预期 +4/s，**两种测法完全吻合**

**方法3 驱动自身节奏**：`check_shutdown_delay` 10s 命中 54 次 = **5Hz**，与步骤0 的 178ms 间隔一致。

### 36. ★结论与优化：上段可做到零 I2C
- 原设计 1Hz×4 个 I2C 节点 = **8.4ms/s ≈ 0.84% 单核**常驻，折算约 **0.1%/天**（不致命，但纯浪费）
- **1% = 63.6mAh，500mA 下要走 7.6 分钟** → 30s tick 已有 15 采样点/百分点，**1Hz 过采样 450 倍**
- **关键洞察：上段 `rm>0` 时 `qbot_now ≡ QBOT` 是常数**，公式退化成只依赖 `raw_soc`(缓存) 和 FCC
  → **上段完全不需要 V/I，零 I2C**

**自适应 tick 定稿**（写入方案C §四之二）：
```
上段(raw_soc>0，约97%时间)：tick=30s，只读 raw_soc(108µs)，FCC 每10min刷一次
                            -> 稳态 ≈ 0.0004% 单核，实质为零
底部段(raw_soc==0，约18min)：tick=2s，读 V/I(各2.1ms) -> 0.21% 单核，仅这一小段
```
息屏后系统 suspend，shell `sleep` 被冻结不产生唤醒 → **待机无额外开销**。

**后续优化**：内核模块本就 hook 了 check_shutdown_delay、手握 struct 指针，
而 `[0x844]`(均值电压)/`[0x838]`(电流) 本就是驱动 5Hz 更新好的缓存值
→ 让模块以只读 module_param 导出，watchdog 底部段降到 ~100µs、零额外 I2C。
策略仍留用户态便于迭代，模块只负责暴露已有缓存值。

### 38. ★「用 GKI 源码会不会变砖」——不会，理由与证据
用户提问。结论：**这一步不存在变砖路径。**
1. **全程不写任何分区**。产物是 `.ko`，`insmod` 加载到内存，`rmmod`/重启即消失。
   无 flash、无 dtbo、无 boot 镜像改动。
2. **GKI 源码就是本机内核的源码，不是"通用替代品"**：
   - `/proc/version` = `...-abogki463945075-4k (kleaf@build-host)` → Google 的 Bazel/kleaf 构建，非小米构建
   - 小米自己的模块 vermagic 是 `-gd8653a69a3aa-mi-4k`，**与运行内核 release 串不一致却照常加载**
     → 这正是 GKI 设计：内核二进制来自 Google，厂商模块按 KMI 单独编译后装入
   - **`mibbr.ko` 本身就是活证据**（OOT kprobe 模块，跑在这台内核上）
3. **最坏情况分级**：
   | 出错项 | 后果 |
   |---|---|
   | CRC / vermagic 不匹配 | `insmod` 报错退出，**什么都没发生** |
   | 结构体布局 / kCFI 错 | 内核 panic → **自动重启，模块不在了**（未落盘） |
   | 偏移错 | 步骤0 已在真机运行时坐实 |
4. **⚠️唯一需要留意的风险点**：打包成 KernelSU 模块**开机自动 insmod** 后，
   才存在「开机即 panic → 循环重启」的可能。
   → **该步必须等手动加载反复验证稳定后再上**；KernelSU 有音量下键安全模式可禁用全部模块兜底。

### 49. ★★验收关卡当场抓出一个错误假设：GENDWARFKSYMS

vmlinux 编译成功，Module.symvers 9079 条。**但 CRC 与 donor 全部对不上**：
```

_printk           0x92997ed8   0x16b5b21d
memset            0xdcb764ad   0x110f4d3a
```
`_printk`(`int(const char*,...)`) 和 `memset` 这种签名不可能跨 build 不同 → 问题在**CRC 生成方式**本身。

**根因**：
```
真机:  CONFIG_GENDWARFKSYMS=y   # CONFIG_GENKSYMS is not set   DEBUG_INFO_DWARF5=y
我们:  CONFIG_GENKSYMS=y        CONFIG_DEBUG_INFO_NONE=y
```
本内核用 **`GENDWARFKSYMS`**——从 **DWARF 调试信息**生成符号版本，而非传统 genksyms 解析源码。
§43 关掉 DEBUG_INFO 后，Kconfig **静默回退到 genksyms**，两套算法 CRC 自然完全不同。

**→ §43 里「关闭 BTF/调试信息对 CRC 是零影响」这句话是错的，已作废。**
这正是 §39 四道验收关卡的价值：错误假设在 insmod 之前就被抓住，而不是在真机上。

### 62. ★★★用两侧 BTF 做对等比对：1593 个可达类型无一不同
两边现在都有 BTF，用**同一个 bpftool** 做真正对等的比对（去掉 `___N` 去重后缀）：
```
struct module           : 完全一致（83 行）
struct modversion_info  : 完全一致
struct kernel_param     : 完全一致
struct kernel_symbol    : 完全一致
struct tracepoint       : 完全一致
```
再用 `tools/btf_reachable_diff.py` 从这 5 个根类型做 BFS 求可达闭包：
```
可达类型闭包 = 1593 个
可达且定义不同 = ★0 个
仅单侧存在的可达类型 = 0 个
```

**→ 结论：`module_layout` 的 CRC 差异，在 BTF 粒度上找不到任何对应的类型差异。**

**原因分析（为什么 BTF 看不出来）**：
1. **BTF 是 DWARF 的有损投影**：不编码对齐属性（`__aligned__`）、const/volatile 限定的部分细节、
   typedef 链等，而 gendwarfksyms 用的是完整 DWARF
2. **BTF 是全内核去重合并的**，gendwarfksyms 用的却是**定义 `module_layout` 的那个编译单元
   自身的 DWARF**。小米对该 CU 所包含头文件的任何改动，都会改变类型展开而在合并后的 BTF 上看不出来

**关键逻辑约束**：`register_kprobe`/`unregister_kprobe`/`_printk`/`memcpy`/`memset`/`__stack_chk_fail`
六个 CRC **全部精确匹配** → 算法与其选项完全一致，不是工具或配置问题；
只有类型图最大（1593 个类型）的 `module_layout` 受影响 → 差异极可能来自小米未公开的 GKI common 补丁。

### 64. 用户决策：改写 module_layout CRC（2026-08-04）
用户在三个选项（改写CRC / 继续找小米GKI源码 / 先只做watchdog）中选择**改写 CRC**。
依据即 §63 的表：设备自己的 BTF 已在字段级证明相关结构体完全一致，比 CRC 这个哈希更直接。

**先澄清了两个问题（用户问「对不上会发生什么，可以绕过吗」）**：
- **对不上 = 干净拒绝**：`check_version()` 不匹配 → `pr_warn("disagrees about version of symbol %s")`
  → `resolve_symbol()` 返回 `-ENOEXEC` → insmod 失败退出。**模块不会被加载，零代码执行，零内存改动。**
  所以直接试 insmod 本身是零风险的。
- **三条绕过路径，本机只有一条可用**：
  | 方式 | 可用性 |
  |---|---|
  | `insmod --force` / `MODULE_INIT_IGNORE_MODVERSIONS` | ❌ 需 `CONFIG_MODULE_FORCE_LOAD=y`，本机未设 |
  | 删除整个 `__versions` 段 | ❌ 同样走 `try_to_force_load()`，仍需该 config |
  | **改写 `__versions` 里的 CRC 值** | ✅ 唯一可行 |
- **CRC 是断言不是机制**：改它不改变任何运行行为，只是让内核不再拒绝。
  判断错的后果是 panic → 自动重启（未落盘，非砖）。

工具：`tools/patch_crc.py`（同时处理 `__versions` 与 `__version_ext_crcs` 两张表）。

### 71. ★★用户指出的关键缺陷：模块单独用不管用

**关机有两条独立路径**：
| 路径 | 触发 | 内核模块管得着吗 |
|---|---|---|
| (a) 内核电压闸 | `mean_volt ≤ vcutoff_delay` → 发 uevent | ✅ 已降到 2700 |

（此前把 watchdog 排在任务#4、当作"显示优化"，优先级判断错了。）

**顺带发现 watchdog 里一个会让整件事失效的 bug**：

**写 0 = 亲手触发 (b)**，前面全部白做。已改为**永不写 0**（最低钳到 1），
关机只走 handoff 写 -1 那条路。

### 73. ⚠️★下一步必须先补的安全缺口：当前是 fail-unsafe
**风险**：watchdog 若在底部被 SIGKILL（不触发 trap），会同时导致

→ **在做任何真正的深放测试之前必须先加这个。**

### 77. ★补 fail-safe（任务#6）——两层设计与「3.0V 会不会关机」
用户问「补上会不会导致在 3.0V 关机」。答案：
| 情况 | 3.0V 时 |
|---|---|
| watchdog 活着 | **不会**。低压兜底阈值 = `vcut+30` = 2730mV，离 3000mV 差 270mV |
| watchdog 死了 | **会，约 3.03V 关机** —— 这是刻意的 |

第二种情况的意义：watchdog 一死，`fake_soc` 卡在非零 → 框架看不到 0% 不关机 +
内核跳过发 uevent → **手机进入"无任何软件闸"状态，一路放到硬件保护**。
fail-safe 把它拉回原厂行为，是**从失控回到安全**，不是功能倒退。

**两层实现**：
| 层 | 触发 | 覆盖 |
|---|---|---|
| 1 心跳超时 | watchdog 每 tick 写 `kick`；约 180s（900 次命中 @5Hz）不变即判死 | **任何电压** |
| 2 低压兜底 | `mean_volt ≤ ref_delay + 30` 且**连续 10 次**（约 2s） | 底部 |

连续计数是必需的：3A×40mΩ≈120mV 瞬时压降，不加计数可能在 OCV 还有 2850mV 时误触发。
计时单位统一用 kprobe 命中次数（~5Hz），避免依赖 `jiffies` 等额外符号（省一个 CRC 依赖）。
新增只读遥测 `t_failsafe`(0/1/2) 与 `t_no_kick`。

**改代码时发现并修掉的两个原有缺陷**：
1. fail-safe 若放在 `!enable` 的 return 之后 → `enable=0` 时不生效，
   但 watchdog 那时仍会化妆、同样堵住关机通道。**已移到 enable 判断之前**，
   且参照阈值取**结构体里实际的 delay**（`rd32(s, OFF_VCUT_DELAY)`）而非我们的参数 ——
   那才是内核真正用于判关机的值（enable=0 时它是原厂 3030）。
2. watchdog 原本只检查 `armed` 不检查 `enable` → `enable=0` 时照样化妆，
   等于"关机点还在 3030 却假装底部有电"。**已补上 enable 检查。**

**顺带纠正一个常见误解**：`FCC 6208 vs 设计 7500` 的差距**不是充电电压降级造成的**，
是电量计学习出的真实衰减 + 计量口径差异。伪装循环改不了 FCC。

留 1 当保险即可（成本为零），可用 `smartchg_delta_fv` 是否非 0 判断以后是否触发降压。
**副作用**：`[0x84c]` 也是 update_cc_para 选档用的值，伪装成 1 后若模块被卸载，

#### 86.3 ★vpack 闸：简单位移是错的（差点写错内存）
`0x8e8 + 0x1A8 = 0xa90`，但反汇编证明新代码测的是 **`0xa91`**：
```asm
9d28:  ldrb  w8, [x19, #0xa91]
9d2c:  cmp   w8, #0x1
9d30:  b.ne  0x9d9c              ← ≠1 就跳过整个 vpack 分支
9d34:  ldr   w21, [x19, #0xb80]
9d50:  cmp   w21, #0xbb8         ← 0xbb8 = 3000，就是那道硬闸
```

全模块引用统计：**`0xa91` 只有 2 处**（parse_dt 里 1 次写 + 这里 1 次读）→ 写 0 是外科手术式的；

**它现在是 1**（旧系统是 0）：小米在 OS4.0 的 DTS 里启用了 `support-vpack-low-shutdown`。
→ `kill_vpack_gate=1` 从"保险措施"变成**必需项**，否则到 3000mV 就被硬闸强关，2620 的闸没机会生效。

### 88. ★运行时偏移自解析（2026-08-29）—— 系统更新后不用回电脑了

**动机**：用户提出"每次更新系统都得重新修补"，并给了参考
`https://github.com/wxxsfxyzm/MiuiBackGestureHook`。
该项目最值得抄的是它的三条工程约定：
```
4371 static profile; validated newer builds use the runtime resolver
Unsupported or ambiguous layouts fail closed
```
——已知版本查表、新版本运行时解析、解析不出来就拒绝，绝不猜。这与本项目的
安全红线天然一致，于是照这个思路给偏移适配做了运行时解析。

**核心矛盾**：偏移是编译期常量（`#define OFF_MEAN_VOLT 0x9fc`），编译进指令里，
运行期改不了。所以"手机上自动修补"不能是"改 .ko 文件"，只能是
**模块加载时自己从目标函数的机器码里把偏移读回来**。

#### 88.1 为什么用语义锚点，不用指令位置
硬编码位置（如 `probe+0x07c`）在函数体被重排时立刻失效。改为匹配
**驱动源码语义在汇编里的投影**，这些模式在已观测的三次 build 变化中全部成立：

| 锚点 | 汇编模式 | 源码语义 |
|---|---|---|
| A | `ldr wD,[x19,#imm]` … `add wD,wD,#50` … `cmp wM,wD` | `mean_volt <= vcutoff_delay + 50` |
| B | `cmp wZ,#3000` ／ `ldrb wG,[x19,#imm]` + `cmp wG,#1` | `vpack_low_en==1 && vpack<=3000` |
| C | `ldr wR,[x19,#imm]` + `cmn wR,#1` | `fake_soc == -1` |

★锚点C 是新发现的：dump `+0x2a8` 处
```
ldr  w8, [x19, #0xb04]
cmn  w8, #1            ← 与 -1 比较，正对应 check_shutdown_delay 里的 fake_soc==-1 判断
```

得到 5 个定值（mean_volt/vcut_delay/vpack/gate/fake_soc）后，用
`delta = 解析出的 mean_volt − 编译期基线 mean_volt` 推导其余 11 个字段。

#### 88.2 内核里手写 AArch64 指令解码
内核没有反汇编器，也不能引 capstone，所以手写解了需要的 6 条。每个掩码都对着
真机反汇编验算过（例：`0xb94b0668` → imm12=0x2c1, ×4=0xb04, Rn=19, Rt=8，
即 `ldr w8,[x19,#0xb04]`）：

| 指令 | mask | value |
|---|---|---|
| `ldr wRt,[xRn,#imm*4]` | 0xffc00000 | 0xb9400000 |
| `ldrb wRt,[xRn,#imm]` | 0xffc00000 | 0x39400000 |
| `add wRd,wRn,#imm` | 0xff800000 | 0x11000000 |
| `cmp wRn,#imm` (Rd=ZR) | 0xff800000 | 0x71000000 |
| `cmn wRn,#imm` (Rd=ZR) | 0xff800000 | 0x31000000 |
| `cmp wRn,wRm` (Rd=ZR) | 0xff000000 | 0x6b000000 |
| `ret` | 0xfffffc1f | 0xd65f0000 |

扫到 `ret` 提前收尾（防越界），上限 256 条指令。全程只读内核代码段，不写任何内存。
实现手法是**寄存器级数据流追踪**：记录每个 w 寄存器最近一次从 `[x19,#imm]` 加载的
偏移与位置，锚点指令命中时回溯取用（要求距离 ≤10 条，避免跨分支误配）。

#### 88.3 两级校验与决策表
```
解析成功 + 指纹通过 -> 用解析值（应与基线相同，delta=0）
解析成功 + 指纹不符 -> ★自愈成功：新 build，用解析值
解析失败 + 指纹通过 -> 用基线（指纹已证明基线正确）
解析失败 + 指纹不符 -> 拒绝加载（没有任何证据支持偏移正确）
```
最后一行是安全底线。另在 `validate()` 里**新增 fake_soc 取值范围校验**
（只能是 -1 或 0..100）：fake_soc 是锚点C 单独定的、且是本模块唯一主动写的
用户可见字段，锚点万一失效就必须有独立复核兜住。

#### 88.4 验证（解析器跑在内核里，上机前必须先证明）
1. **用户态干跑**：`tools/resolver_dryrun.py` 把解析逻辑逐行照搬成 Python，
   对真机模块跑出 5/5 锚点命中、16 项与人工逆向**完全一致**。
2. **合成自愈回归**：`tools/test_selfheal.py` 把函数里所有 `[x19,#imm]` 立即数
   整体平移，合成"未来的 build"再解析。**13/13 通过**：
   - 正向 +0x4/+0x10/+0x20/+0x40/+0x100
   - 负向 −0x4/−0x10/−0x40
   - ★gate 例外（额外 ±1）：位移结果会落在前一个高频标志上，锚点每次都拉回来了
   这一步是必要的：只测当前 build 只能证明"能复述已知答案"，测不了未知变化。
3. **真机自愈实测**（`tools/make_stale_variant.py`）：把编译期基线**人为改错 +0x10**
   （等于制造"系统更新后基线过时"），编译加载后：
   ```

   校验通过 fw=3130 ... fake_soc=-1 (偏移源=运行时自解析 delta=-16)
   armed=1 t_resolved=1 t_delta=-16 t_anchors=31(0x1f) t_off_src=1
   ```
   全部 16 项被拉回真值 —— 特别是 gate：基线是 `0xab1`（位移结果、错），
   锚点定出 `0xaa1`（真值），正是那个 8 处引用的高频标志被避开了。
   tracefs 直读复核：`fw=2620 dly=2620 sw=2520 vpen=0`、`cutoff_vol=2620`。
4. **真实重启**：`t_resolved=1 t_anchors=0x1f t_delta=0 armed=1`，
   `boot.log` 记 `insmod rc=0` / `armed=1 校验通过`。

#### 88.5 现在的行为
- **vendor 模块换 build（struct 挪位）→ 手机上自动适配，不用回电脑**。
- **GKI 换内核 → 仍需回电脑**：CRC 对不上（`rc=8`），编译期的事运行期解决不了。
- 两种失效可以从 `boot.log` 的返回码立刻区分：`rc=8` 是 CRC/ABI，
  `rc=19`（ENODEV）是偏移/锚点。

#### 88.6 走过的弯路
- 一开始理解成"在电脑上写自动化流水线"，做了 adb 封装/profiles/CRCsan 一套，
  用户澄清要的是"手机上自包含、不依赖电脑"，方向纠正后才做运行时解析。
  教训：**先确认"在哪一端执行"**，这决定了整个方案的形态。
- `make_stale_variant.py` 第一版用 `;` 结尾的正则，把 `OFF_VPACK_LOW_EN` 那行
  **行尾的注释**丢掉了（它的注释还跨到下一行），编译报 19 个错。
  改正则捕获 `;` 之后的内容才对 —— 生成源码变体的脚本要保留行尾注释。
- 新增的 `__stack_chk_fail` / `memset`（编译器给数组加的栈保护）CRC
  与 donor 一致，四关照过。

  它跑在内核里，出 bug 就是写错内核内存。

  （紧贴 delay 的簇）。下次若连 delay 锚点都命中不了（驱动改了判断语义），
  仍需回电脑 dump 新函数体重找锚点——这条底线不变。

#### 89.8 重启后模块"消失"——KSU modules_update 是【整目录替换】（踩坑+修正）
首次重启后模块不见了，`boot.log` **当天无任何新行**（service.sh 根本没跑）。
排查：`/data/adb/modules/vcut_lower/` 里**只剩 `vcut_lower.ko`**，
service.sh / action.sh / module.prop / uninstall.sh / META-INF 全没了。

**根因（我的安装失误）**：装新 .ko 时我 `mkdir modules_update/vcut_lower && cp 只放了 .ko`。
KernelSU 重启时把 `modules_update/<id>/` 当作**该模块的完整新内容**，**整目录搬去替换**
`modules/<id>/` —— 于是除 .ko 外的脚本全被抹掉。没有 module.prop → KSU 管理器里"消失"；
没有 service.sh → 开机无人加载。（`disable`/`bootfail` 都正常，.ko 本身 sha 也对。）

**正确姿势（二选一）**：
- 只换 .ko：**直接写 `modules/<id>/vcut_lower.ko`**（模块已挂载的活动目录），不要走 modules_update；
- 走 modules_update：**必须放整套文件**（module.prop/service.sh/action.sh/uninstall.sh/META-INF/…），
  不能只放 .ko。

**修正**：把 `ksumodule/` 全套 push 回 `modules/vcut_lower/`（保留已正确的 .ko），
strip CRLF + chmod 0755/0644；module.prop 版本顺手升到 `v1.4-2620-os4.0.0.32`。
之后手动跑 service.sh 复核开机路径。
